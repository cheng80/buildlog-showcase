# 소개 사이트 문서·제작 작업 흐름

> 첨부 Lite의 정본 분리와 검증·인수인계 방식을 소개 사이트 범위에 적용한다.

## 1. 정본

| 정보 | 위치 |
|---|---|
| 목적·타깃·카피·FR·BR·화면·이미지 프롬프트 | [01_PRODUCT_SPEC.md](01_PRODUCT_SPEC.md) |
| 소개 사이트의 구현 방식·제약 | [02_TECH_SPEC.md](02_TECH_SPEC.md) |
| 작업·진행·알려진 문제·검증·인수인계 | [03_PROJECT_STATUS.md](03_PROJECT_STATUS.md) |
| 작업·변경 절차 | 이 문서 |
| AI 작업 시작 경로 | [AGENTS.md](../AGENTS.md) |

실제 서비스의 제품·기술 기획은 이 문서 묶음에 작성하지 않는다.

## 2. 기획에서 제작까지

1. 기획서에서 목적·범위·카피·섹션·완료 기준을 읽는다.
2. ASCII에서 읽기 순서와 CTA 목적지를 확인한다.
3. 필요한 화면의 `IG-xxx` 또는 `UI-xxx` 프롬프트와 대응 ASCII를 함께 사용해 시각화한다. 모든 프롬프트를 한 번에 실행할 필요는 없다.
4. 생성 결과를 검토하고 한글·예시 라벨·정보 순서·동일 프로젝트 표현을 바로잡는다.
5. 실제 사이트 제작 요청이 있으면 기술 전제를 확인하고 소개 사이트를 구현한다.
6. 요구사항과 실제 화면을 검증한 뒤 현황과 인수인계를 갱신한다.

## 3. 시각화 검토 기준

- 각 `WF-xxx`의 구성과 대응 `IG-xxx` / `UI-xxx` 결과가 일치한다.
- ‘작은 타이머’와 대표 개발 기록이 화면 간에 일관된다.
- 이미 있는 프로덕트를 홍보하는 톤이다. ‘개발 예정’·‘콘셉트’·개발 기간 같은 제작 상태 표현이 없고, 허구의 실적·이용자·후기도 추가되지 않는다.
- 생성 이미지의 한글을 검수한다. 읽기 어려우면 텍스트 없는 이미지에 검수된 카피를 별도로 얹는다.
- 실제 웹페이지의 주요 텍스트·CTA는 이미지에만 의존하지 않는다.
- 실제 자산이 생겼을 때만 `docs/assets/`를 만들고 원본·선택본의 용도를 구분한다.

## 4. 변경 처리

- 카피·구성 변경: 기획서의 카피 → 관련 ASCII → 대응 프롬프트 → 완료 기준 순서로 확인한다.
- 기술 변경: 관련 `FR` / `BR` 영향 확인 → 기술 명세 → 실제 구현과 검증 결과 반영.
- 현황 변경: 진행률·완료·미실행은 현황 문서만 갱신한다.
- 중요한 선택의 이유를 따로 보존할 필요가 있을 때만 `decisions/ADR-xxx.md`를 만든다.
- 별도 설계가 필요한 복잡한 작업에만 `plans/PLAN-xxx.md`를 만든다. 빈 템플릿을 추가하지 않는다.

## 5. 종료와 인수인계

이번처럼 문서만 만드는 작업은 문서 범위·누락·내부 링크·ID·프롬프트 대응·ZIP 무결성을 검증한다. 실제 사이트 검증과 혼동하지 않는다.

사이트 제작 후에는 필요한 검증을 실행하고 결과를 `PASS / FAIL / INCOMPLETE / NOT_RUN / UNKNOWN`으로 기록한다. 근거·날짜·리비전·유효성·공백을 함께 남기며 미실행을 통과로 쓰지 않는다.

현황의 인수인계에는 완료 내용, 남은 자료, 변경하면 안 되는 범위, 바로 할 일, 검증 상태를 남긴다. 같은 내용을 별도 인수인계 파일로 복제하지 않는다.
