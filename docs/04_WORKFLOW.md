실제 서비스의 제품·기술 기획은 이 묶음에 쓰지 않는다.

## 2. 기획에서 제작까지

1. 기획서 4절 카피와 예시 콘텐츠, 6절 ASCII로 섹션 순서와 화면 구성을 확인한다.
2. `DESIGN.md` 토큰을 CSS 변수로 옮기고 섹션을 구현한다. 시각 자료는 HTML/CSS로 직접 그린다.
3. 기술 명세 5절 검증을 실행한다.
4. **첫 화면 테스트:** 기획을 모르는 사람의 눈으로 첫 화면만 보고 ‘무슨 서비스인지’ 한 문장으로 말할 수 있는지 확인한다(`BR-007`). 말할 수 없으면 카피나 화면을 고친다.
5. 현황 문서의 검증 표와 인수인계를 갱신한다.

## 3. 변경 처리

- **카피·구성:** 기획서 카피 → 예시 콘텐츠 → ASCII → 완료 기준 순서로 함께 고친다.
- **디자인:** `DESIGN.md`를 먼저 고치고 CSS 변수에 반영한다.
- **기술:** 관련 FR/BR 영향 확인 → 기술 명세 → 구현·검증.
- **현황:** 진행·완료·미실행은 현황 문서에만 기록한다.
- 결정 이유를 따로 남길 필요가 있을 때만 `decisions/ADR-xxx.md`, 복잡한 작업에만 `plans/PLAN-xxx.md`를 만든다.

## 4. 검증 기록

결과는 `PASS / FAIL / INCOMPLETE / NOT_RUN / UNKNOWN`으로, 근거·날짜·리비전·공백과 함께 남긴다. 미실행을 통과로 쓰지 않는다. 문서 검증과 사이트 검증을 섞지 않는다.
