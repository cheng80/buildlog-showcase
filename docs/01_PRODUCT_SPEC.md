# 프로젝트 쇼케이스 · 소개 사이트 기획서

> 문서 버전: 1.2 · 작성일: 2026-09-16 · 상태: 소개 사이트 제작 기준안
>
> 이 문서의 기획 대상은 **‘프로젝트 쇼케이스’ 서비스를 알리는 프로덕트 홍보 홈페이지**다. 사이트는 이미 사용할 수 있는 프로덕트를 소개하는 톤으로 만든다. 파일명은 첨부 Lite 문서 체계를 따른다. 실제 서비스의 제품 기획서가 아니다.

## 1. 프로젝트 한 줄 정의

**개발 기록이 프로젝트 홍보로 이어지는 서비스를, 짧은 설명과 실제 서비스 화면으로 소개하는 프로덕트 홍보 사이트.**

| 항목 | 기획 내용 |
|---|---|
| 소개할 프로덕트 | 개인·인디 개발자와 소규모 개발팀·개발사가 만드는 과정을 공유하고, 그 기록을 프로젝트별로 모아 알리는 서비스 |
| 소개 사이트의 목적 | 처음 방문한 사람이 이 서비스가 무엇인지, 왜 필요한지, 어떻게 쓰는지 바로 이해하게 한다. |
| 핵심 메시지 | 개발 기록이 프로젝트 홍보가 된다. |
| 첫 화면 제목 | **개발 기록으로 프로젝트를 알리다** |
| 첫 화면 대상 문구 | 인디 개발자와 작은 개발팀을 위한 서비스 |
| 보조 설명 | 이미지, 영상, 짧은 글로 만드는 과정을 공유하세요. 기록이 쌓일수록 프로젝트의 이야기가 한곳에 모입니다. |
| 주 행동 | **화면 둘러보기** → 같은 페이지의 `#preview` |
| 사이트 톤 | 출시된 프로덕트의 홍보 페이지. 기능과 경험을 현재형으로 설명한다. 개발 기간·진행 상태·공개 일정은 사이트에 노출하지 않는다. |
| 표기 이름 | 정식 이름 확정 전에는 **프로젝트 쇼케이스** 사용 |

첫 화면 제목은 4어절로, 짧고 직관적인 설명 방향을 반영한다. 다른 서비스를 알아야 이해할 수 있는 비교 문구는 쓰지 않는다.

## 2. 목표 / 제외 범위

### 목표

- 첫 화면에서 **개인·인디 개발자와 작은 개발팀 대상 / 개발 과정 공유 / 프로젝트 알리기**를 파악할 수 있다.
- 문제 → 해결 → 서비스 화면 → 시작 방법을 한 번의 스크롤로 이해한다.
- 한 개의 예시 프로젝트로 일관되게 구성한 서비스 화면으로, 실제로 쓰는 모습을 완성도 있게 보여준다.
- 이후 사이트 제작에 사용할 카피, 화면 구조, 이미지 생성 프롬프트를 한곳에 둔다.

### 이번 산출물의 범위

소개 사이트는 **단일 랜딩 페이지**로 기획한다. 로그인, 프로젝트 등록·편집, 피드 게시, 결제·취소·내역, 지도, 추천 알고리즘, 콘텐츠 자동화 파이프라인은 이 사이트에서 구현하지 않는다. 해당 기능의 데이터·API·운영 정책도 설계하지 않는다.

## 3. 타깃과 방문 목적

**핵심 사용자는 자신이 만드는 앱·웹·게임 등의 프로젝트를 직접 소개하고 홍보해야 하는 개인·인디 개발자와 소규모 개발팀·개발사다.** 개발 기록을 작성하는 사람이면서 프로젝트를 알리는 주체다.

주요 기준은 유명세나 회사 규모 자체보다 **자신의 프로젝트를 지속적으로 알릴 필요가 있는가**다. 여기서 소규모 개발사는 자체 프로젝트나 공개 가능한 제작 결과를 꾸준히 소개하려는 팀을 뜻한다.

### 서비스가 지향하는 사용자

| 사용자 | 필요한 이유 | 소개 사이트가 보여줄 경험 | 방문 후 기대 행동 |
|---|---|---|---|
| 1차: 개인·인디 개발자 | 혼자 만든 프로젝트의 과정과 변화를 꾸준히 알리고 싶다. | 짧은 기록 하나가 프로젝트 소개로 이어지는 모습 | 자신의 프로젝트에 쓸 수 있는지 서비스 화면 확인 |
| 1차: 소규모 개발팀·개발사 | 팀이 만드는 프로젝트의 진행 과정과 결과를 한곳에서 보여주고 싶다. | 여러 개발 기록이 한 프로젝트의 이야기로 모이는 모습 | 팀 프로젝트를 알리는 방식인지 확인 |
| 2차: 새로운 앱·웹·게임에 관심 있는 사람과 동료 개발자 | 흥미로운 프로젝트를 발견하고 어떤 과정을 거쳤는지 보고 싶다. | 시각적인 기록과 프로젝트의 변화 | 서비스 화면을 보고 취지 이해 |

카피는 먼저 ‘만드는 사람에게 왜 필요한가’를 설명하고, 다음으로 ‘그 프로젝트를 발견하는 경험’을 보여준다. 위 사용자 설명은 홍보 메시지를 정하기 위한 수준이며 별도의 서비스 기능 명세로 확대하지 않는다.

## 4. 핵심 사용자 흐름과 페이지 구조

방문자는 첫 화면의 제목을 읽고 **화면 둘러보기**로 바로 이동하거나, 아래로 스크롤하며 필요성부터 확인한다. 마지막에는 서비스 화면을 다시 보거나 페이지 처음으로 돌아간다. 이 사이트 안에서 가입이나 개인정보 입력은 받지 않는다.

### 페이지 / 섹션 구성

| 순서 | ID / 주소 | 역할 | 핵심 콘텐츠 | 다음 행동 |
|---|---|---|---|---|
| 상단 | `#top` | 이름·빠른 이동 | 프로젝트 쇼케이스 / 소개 / 화면 / 시작하기 | 각 앵커로 이동 |
| 1 | `S-01` · `#hero` | 누구를 위한 무엇인가 | 대상 문구, 핵심 제목, 보조 설명, 서비스 비주얼 | `#preview` 또는 아래로 읽기 |
| 2 | `S-02` · `#why` | 왜 필요한가 | 흩어진 기록, 별도 홍보의 부담 | `#how` |
| 3 | `S-03` · `#how` | 어떤 경험인가 | 기록하기 → 모아보기 → 발견되기 | `#preview` |
| 4 | `S-04` · `#preview` | 실제로 어떻게 보이나 | 같은 기록이 보이는 피드 화면과 프로젝트 화면 | `#start` |
| 5 | `S-05` · `#start` | 어떻게 시작하나 | 프로젝트 만들기 → 기록 올리기 → 프로젝트 알리기 | `#faq` |

| 7 | `S-07` · `#closing` | 무엇을 기억할까 | 짧은 마무리 문구와 반복 CTA | `#preview` |
| 하단 | 푸터 | 이름·이동 | 프로젝트 쇼케이스 / 핵심 메시지 / 이미지 출처가 있으면 표기 | `#top` |

한국어를 기본으로 한다. 제목은 짧게, 설명은 1~2문장으로 쓴다. 제작자의 기술 스택보다 방문자가 얻게 될 경험을 먼저, 현재형으로 설명한다.

| S-01 상단 라벨 | 개발 기록 공유 서비스 |

## 5. 소개 사이트 기능 요구사항

### FR-001 페이지 읽기와 섹션 이동

- **목적:** 필요한 설명이나 서비스 화면에 바로 접근한다.
- **동작:** 상단의 소개(`#how`)·화면(`#preview`)·시작하기(`#start`), 첫 화면의 두 링크, 마지막 CTA가 위 표의 앵커로 이동한다. 로고와 ‘처음으로’는 `#top`으로 이동한다.
- **조건/규칙:** 버튼·링크 문구와 목적지가 일치한다. 고정 헤더 사용 시 도착한 제목이 가려지지 않는다.
- **예외:** 스크립트가 실행되지 않아도 본문과 앵커 링크를 읽고 사용할 수 있다.
- **완료 조건:** 모든 링크가 존재하는 섹션으로 이동하며 모바일에서도 제목이 보인다.

### FR-002 서비스 화면 소개

- **목적:** ‘기록 → 프로젝트에 축적’이라는 관계를 시각적으로 이해한다.
- **동작:** 피드 화면과 해당 프로젝트 화면을 정적 이미지 또는 비상호작용 카드로 함께 보여준다.
- **조건/규칙:** 두 화면에서 프로젝트 이름·대표 이미지·개발 기록이 일치한다. 화면은 실제 서비스 화면처럼 완성도 있게 보여주고, 예시 프로젝트라는 점은 하단의 작은 캡션 텍스트로만 알린다.
- **예외:** 이미지가 없거나 로딩에 실패해도 프로젝트 이름·기록 내용·설명은 남는다. 영상 기록은 썸네일로 표시하며 재생 기능을 두지 않는다.
- **완료 조건:** 설명만으로 연결 관계를 이해할 수 있고, 화면 내부 요소가 실제 버튼처럼 동작하지 않는다.

### FR-003 자주 묻는 질문

- **목적:** 올릴 수 있는 프로젝트, 사용 대상, 기록이 쌓이는 방식을 명확히 한다.
- **동작:** 질문 3개를 펼쳐 읽는다. 질문은 모두 독립적으로 열 수 있고 첫 질문은 기본 펼침이다.
- **조건/규칙:** 키보드로 열고 닫을 수 있으며 열림 상태를 인식할 수 있다.
- **예외:** 스타일이나 스크립트가 없어도 질문·답변에 접근할 수 있다.
- **완료 조건:** 아래 답변이 모두 표시된다.

| 질문 | 답변 |
|---|---|
| 어떤 프로젝트를 올릴 수 있나요? | 앱, 웹, 게임처럼 직접 만들고 있는 프로젝트라면 올릴 수 있습니다. 완성 전이라도 만드는 과정부터 기록할 수 있습니다. |
| 누구를 위한 서비스인가요? | 자신의 프로젝트를 직접 만들고 알리는 인디 개발자와 소규모 개발팀, 개발사를 위한 서비스입니다. 새로운 프로젝트를 발견하고 싶은 사람도 개발 기록을 살펴볼 수 있습니다. |
| 기록은 어떻게 쌓이나요? | 이미지, 영상 링크, 짧은 글로 올린 기록은 피드에 보이고 같은 기록이 프로젝트 페이지에 순서대로 모입니다. |

### FR-004 모바일과 대체 표현

- **목적:** 작은 화면이나 이미지 누락 상황에서도 같은 메시지를 전달한다.
- **동작:** 넓은 화면의 2~3열 콘텐츠를 모바일에서는 본문 순서대로 1열로 배치한다.
- **조건/규칙:** 본문을 이미지에만 넣지 않는다. 포커스 표시, 읽기 쉬운 대비, 이미지 대체 설명을 제공한다. 자동 재생과 필수 스크롤 애니메이션은 없다.
- **예외:** 긴 한국어 제목은 자연스럽게 줄바꿈한다. 이미지 영역은 비율을 유지하되 대체 설명을 가리지 않는다.
- **완료 조건:** 360px·390px·768px·1440px에서 가로 넘침 없이 읽을 수 있고, 키보드로 모든 실제 링크와 FAQ를 이용할 수 있다.

## 6. 화면 명세 · ASCII 와이어프레임 · 이미지 생성 프롬프트

### 공통 시각화 방향

- **분위기:** 출시된 프로덕트의 정돈된 홍보 페이지. 따뜻한 흰색 배경, 진한 먹색 글자, 청록색 강조, 차분한 회색 구분선. 이는 제작용 제안이며 확정된 브랜드 가이드는 아니다.
- **구성:** 넓은 여백, 큰 한국어 제목, 실제 서비스를 쓰는 모습이 보이는 완성도 있는 화면. 코드 장식이나 추상적인 3D 오브젝트보다 기록과 프로젝트의 관계를 강조한다.
- **예시 프로젝트:** **작은 타이머** — 집중 시간을 기록하는 앱. ‘집중 화면을 더 단순하게 바꿨어요’라는 동일 기록을 피드와 프로젝트 양쪽에 사용한다.
- **이미지 생성 방식:** 아래 각 와이어프레임에 인포그래픽용 `IG-xxx`, UI 목업용 `UI-xxx` 프롬프트를 바로 붙였다. 필요할 때 해당 프롬프트와 와이어프레임을 함께 전달한다.
- **이미지 공통 금지:** ‘개발 예정’, ‘콘셉트’, ‘준비 중’, ‘예시’ 같은 제작 상태 라벨, 개발 기간·날짜, 이용자 수·후기·반응 수치·가격, 프롬프트에 없는 슬로건·태그·영문 장식 문구.
- **인포그래픽의 버튼 금지:** `IG-xxx`는 구조와 흐름을 설명하는 그림이다. 버튼·CTA 알약 모양·‘처음으로’ 같은 링크 등 눌러야 할 것처럼 보이는 요소를 그리지 않는다. CTA는 일반 텍스트 라벨이나 화살표·아이콘으로만 표현한다. 와이어프레임의 `[ ]` 버튼 표기와 `-->` 화살표 기호는 그대로 그리거나 글자로 옮기지 않는다. 버튼은 `UI-xxx` 목업에서만 사용한다.
- **비율과 기기 프레임:** 인포그래픽은 가로 16:9 또는 세로 4:5·3:4까지만 쓴다. 9:16처럼 세로로 긴 비율은 사이트에 배치할 수 없으므로 쓰지 않는다. 스마트폰 등 기기 프레임은 실제 기기와 다른 비율로 늘어나기 쉬워 그리지 않는다.
- **텍스트 처리:** 생성 이미지의 한글은 검수하고, 깨지면 글자 없는 이미지로 다시 만든 뒤 실제 텍스트를 얹는다. 최종 웹페이지의 제목·본문·CTA는 이미지에 합치지 않고 접근 가능한 텍스트로 구현한다.
- **목업의 경계:** `UI-006`의 서비스 화면은 홍보용 이미지다. 이를 실제 서비스의 페이지·기능·데이터 명세로 확대하지 않는다.

> 가로 4:3 한국어 문제 설명 인포그래픽을 만들어라. 제목은 ‘만든 것은 많은데, 알리기는 어렵습니다’. 왼쪽에 ‘폴더 속 스크린샷’, 가운데 ‘채널 속 영상’, 오른쪽 ‘흩어진 개발 이야기’ 카드를 두고, 아래 ‘다시 모아 설명하는 시간’ 상자로 연결한다. 위 ASCII의 구조를 유지한다. 따뜻한 흰색 배경, 회색 카드, 먹색 본문, 청록색 핵심 문구. 특정 서비스 로고·통계·비교 우열을 추가하지 말고 개발자의 일상적인 불편을 차분하게 표현한다.

**UI-004 · UI 목업 생성 프롬프트**

> 가로 16:9 한국어 랜딩 페이지의 ‘만드는 이유’ 섹션 목업을 만들어라. 위쪽에 ‘만든 것은 많은데, 알리기는 어렵습니다’를 크게 쓰고 그 아래 3개의 얇은 테두리 카드를 나란히 배치한다. 카드 제목은 ‘폴더 속 스크린샷’, ‘채널 속 영상’, ‘흩어진 개발 이야기’. 아래에는 ‘프로젝트를 소개하려면 다시 모아 설명해야 합니다’를 한 줄로 강조한다. 위 ASCII를 따르고 따뜻한 흰색·먹색·청록을 사용한다. 성과 수치나 버튼을 추가하지 않는다.

### WF-005 S-03 · 핵심 경험

**목적:** 기능 나열 대신 기록이 소개로 이어지는 관계를 전달. **진입:** 스크롤 / `#how`. **주 행동:** 세 단계 읽기. **다음:** 서비스 화면.

```text
+------------------------------------------------------------------------------------+
| 오늘의 기록이 프로젝트 이야기가 됩니다                                             |
|                                                                                    |
| [짧게 기록하기]  -->  [프로젝트에 모으기]  -->  [발견되기]                         |
| 이미지, 영상, 글      프로젝트의 변화          새로운 사람에게 소개                |
+------------------------------------------------------------------------------------+
```

각 카드는 아이콘·짧은 제목·설명 한 문장으로 구성한다. 모바일에서는 같은 순서로 세로 배치한다. ‘발견’은 서비스가 주는 가치로 표현하되 노출량이나 조회수를 보장하는 표현으로 사용하지 않는다. 자동 카드뉴스·유료 홍보 등 확장 아이디어는 이 페이지의 설명에 추가하지 않는다.

**IG-005 · 인포그래픽 생성 프롬프트**

> 가로 16:9의 3단계 한국어 인포그래픽을 만들어라. 제목 ‘오늘의 기록이 프로젝트 이야기가 됩니다’. 위 ASCII대로 ‘짧게 기록하기 → 프로젝트에 모으기 → 새로운 사람에게 발견되기’를 연결한다. 첫 단계는 이미지와 영상 링크와 짧은 글, 둘째는 프로젝트 기록 묶음, 셋째는 프로젝트 카드를 읽는 사람의 간단한 아이콘으로 표현한다. 따뜻한 흰색 배경, 청록 연결선, 먹색 제목. 알고리즘 도식·자동 매출·상승 수치·보장 표현, ‘개발 예정’·‘지향’ 같은 라벨은 넣지 않는다.

**UI-005 · UI 목업 생성 프롬프트**

> 가로 16:9 한국어 웹사이트 가치 소개 섹션을 만들어라. 제목 ‘오늘의 기록이 프로젝트 이야기가 됩니다’ 아래 3개 카드를 같은 크기로 배치한다. 카드 제목은 ‘짧게 기록하기’, ‘프로젝트에 모으기’, ‘새로운 사람에게 발견되기’. 각각 기록 카드 아이콘, 타임라인 아이콘, 프로젝트 발견 아이콘과 짧은 설명 한 줄을 사용한다. 위 ASCII 순서를 따르고 카드 사이 흐름을 작은 청록 화살표로 표시한다. 따뜻한 흰색·먹색, 충분한 여백. 클릭 버튼이나 별도 기능 메뉴는 넣지 않는다.

### WF-006 S-04 · 서비스 화면

**목적:** 같은 기록이 피드와 프로젝트 안에서 연결되는 모습 확인. **진입:** 주 CTA / `#preview`. **주 행동:** 두 화면을 읽고 비교. **상태:** 정적 표시 / 이미지 누락 시 설명 유지.

```text
+--------------------------------------------------------------------------------------+
| 기록 하나가 연결되는 흐름                                                            |
| 피드에 올린 기록은 프로젝트 페이지에도 쌓입니다.                                     |
+--------------------------------------------------------------------------------------+
| 피드                                      | 프로젝트                                 |
|                                           |                                          |
| 작은 타이머                               | 작은 타이머                              |
| [타이머 화면 이미지]                      | 집중 시간을 기록하는 작은 앱             |
| [영상 기록 썸네일]                        | [동일한 타이머 이미지]                   |
|                                           |                                          |
| 집중 화면을 더 단순하게 바꿨어요          | 개발 기록                                |
| 남은 시간을 크게 보여주고                 | - 첫 화면 스케치                         |
| 화면의 요소를 줄였습니다.                 | - 타이머 화면 제작                       |
|                                           | - 집중 화면을 더 단순하게 바꿨어요       |
+--------------------------------------------------------------------------------------+
| 같은 기록이 피드에서 보이고 프로젝트의 변화로 모입니다.                              |
| 화면 속 프로젝트는 예시입니다. (작은 캡션)                                           |
+--------------------------------------------------------------------------------------+
```

화면에 쓰는 콘텐츠는 아래로 고정한다. 조회·좋아요·팔로워 수, 실존 인물 이름과 아바타는 넣지 않는다.

| 요소 | 사용할 내용 |
|---|---|
| 프로젝트 | 작은 타이머 |
| 한 줄 설명 | 집중 시간을 기록하는 작은 앱 |
| 대표 개발 기록 | 집중 화면을 더 단순하게 바꿨어요 |
| 기록 설명 | 남은 시간을 크게 보여주고 화면의 요소를 줄였습니다. |
| 미디어 | 타이머 화면 이미지, 영상 기록의 정적 썸네일 |
| 이전 기록 | 첫 화면 스케치 / 타이머 화면 제작 |
| 하단 설명 | 같은 기록이 피드에서 보이고 프로젝트의 변화로 모입니다. |

좌측 피드와 우측 프로젝트는 **소개 페이지 안의 서비스 화면 이미지**다. 별도 `/feed`, `/project`, `/profile` 페이지를 만들지 않는다. 완성 이미지가 없으면 위 문구를 넣은 텍스트 카드로 먼저 전달한다.

**IG-006 · 인포그래픽 생성 프롬프트**

> 가로 16:9 한국어 인포그래픽을 만들어라. 왼쪽은 ‘피드’ 화면 카드, 오른쪽은 ‘프로젝트’ 화면 카드. 왼쪽에는 ‘작은 타이머’와 ‘집중 화면을 더 단순하게 바꿨어요’라는 기록, 타이머 화면 미니어처, 영상 기록 썸네일을 넣는다. 오른쪽에는 같은 프로젝트 제목, ‘집중 시간을 기록하는 작은 앱’ 설명, ‘첫 화면 스케치 → 타이머 화면 제작 → 집중 화면을 더 단순하게 바꿨어요’ 기록 묶음을 넣는다. 같은 기록의 연결을 청록색 선으로 강조한다. 위 ASCII 배치를 따르고 따뜻한 흰색·먹색을 사용하며 실제 서비스 화면처럼 완성도 있게 그린다. 사용자 이름·아바타·반응 수치, ‘개발 예정’·‘콘셉트’·‘예시’ 라벨은 넣지 않는다.

**UI-006 · UI 목업 생성 프롬프트**

> 가로 16:9 한국어 프로덕트 홍보 사이트의 서비스 화면 섹션 UI 목업을 만들어라. 제목 ‘기록 하나가 연결되는 흐름’ 아래 ‘피드에 올린 기록은 프로젝트 페이지에도 쌓입니다’ 안내를 둔다. 위 ASCII처럼 왼쪽은 큰 이미지가 있는 피드 카드, 오른쪽은 프로젝트 소개와 세 개의 기록이 쌓인 카드로 구성한다. 두 카드에 같은 ‘작은 타이머’ 이름, 타이머 이미지, ‘집중 화면을 더 단순하게 바꿨어요’ 기록을 사용한다. 따뜻한 흰색 배경, 먹색 본문, 청록 연결 강조. 서비스 전체 앱 화면을 설계하지 말고 소개 페이지에 삽입할 정적 화면만 보여라. 로그인·게시·좋아요·영상 재생·결제 버튼과 반응 수치, ‘개발 예정’·‘콘셉트’ 라벨을 넣지 않는다.

### WF-007 S-05 · 시작하기

**목적:** 서비스를 쓰는 흐름을 세 단계로 보여준다. **진입:** 스크롤 / 헤더 ‘시작하기’ / `#start`. **주 행동:** 세 단계 읽기. **상태:** 정적 설명.

```text
+------------------------------------------------------------------------------------+
| 세 단계로 프로젝트를 알리세요                                                      |
|                                                                                    |
| [프로젝트 만들기]  -->  [기록 올리기]  -->  [프로젝트 알리기]                      |
| 이름과 한 줄 설명      이미지, 영상, 짧은 글   쌓인 기록으로 소개                  |
+------------------------------------------------------------------------------------+
```

이 섹션은 서비스 사용 흐름의 개요다. 가입·다운로드 버튼은 실제 주소가 생기기 전까지 두지 않는다(`BR-004`). 단계별 상세 기능·화면 명세로 확대하지 않는다.

**IG-007 · 인포그래픽 생성 프롬프트**

> 가로 16:9 한국어 사용 흐름 인포그래픽을 만들어라. 제목 ‘세 단계로 프로젝트를 알리세요’. 위 ASCII 순서로 ‘프로젝트 만들기 → 기록 올리기 → 프로젝트 알리기’를 3개의 동일한 크기 단계로 표시한다. 각각 ‘이름과 한 줄 설명’, ‘이미지, 영상, 짧은 글’, ‘쌓인 기록으로 소개’ 한 줄 설명과 간단한 화면 아이콘을 붙인다. 따뜻한 흰색 배경, 먹색 글자, 청록 연결선. 날짜·진행률·완료 체크·일정, 사용자 수·성과 수치, ‘개발 예정’ 라벨을 추가하지 않는다.

**UI-007 · UI 목업 생성 프롬프트**

> 가로 16:9 한국어 프로덕트 소개 페이지의 시작하기 섹션 목업을 만들어라. ‘세 단계로 프로젝트를 알리세요’라는 제목 아래 번호가 붙은 3개 카드를 가로로 놓고 ‘프로젝트 만들기’, ‘기록 올리기’, ‘프로젝트 알리기’를 순서대로 배치한다. 각 카드에 작은 서비스 화면 일러스트와 한 줄 설명을 넣는다. 위 ASCII를 따르고 따뜻한 흰색·먹색·청록을 사용한다. 날짜 눈금, 진행 바, 백분율, 가입·다운로드 버튼은 추가하지 않는다.

### WF-008 S-06~07 · 자주 묻는 질문과 마지막 행동

**목적:** 남은 궁금증을 풀고 서비스 화면을 다시 보게 한다. **진입:** 하단 스크롤 / `#faq`. **주 행동:** 질문 펼치기 / `#preview` / `#top`. **상태:** 첫 질문 펼침.

```text
+------------------------------------------------------------------------------------+
| 자주 묻는 질문                                                                     |
+------------------------------------------------------------------------------------+
| [-] 어떤 프로젝트를 올릴 수 있나요?                                                |
|     앱, 웹, 게임처럼 직접 만들고 있는 프로젝트라면 올릴 수 있습니다.               |
|     완성 전이라도 만드는 과정부터 기록할 수 있습니다.                              |
| [+] 누구를 위한 서비스인가요?                                                      |
| [+] 기록은 어떻게 쌓이나요?                                                        |
+------------------------------------------------------------------------------------+
| 만드는 과정부터 보여주세요                                                         |
| 오늘의 기록 하나가 프로젝트를 알리는 첫걸음이 됩니다.                              |
| [화면 둘러보기]  -->  #preview                                                     |
+------------------------------------------------------------------------------------+
| 프로젝트 쇼케이스 · 개발 기록으로 프로젝트를 알리다        처음으로                |
+------------------------------------------------------------------------------------+
```

답변 전체는 `FR-003`의 표를 사용한다. 연락처·제작자 이름·외부 채널은 확인된 정보가 있을 때만 추가한다. 이메일 입력 폼은 기본 구성에 없다.

**IG-008 · 인포그래픽 생성 프롬프트**

> 세로 4:5 한국어 소개 사이트 마무리 인포그래픽을 만들어라. 위쪽에 질문 카드 3개를 배치해 ‘앱, 웹, 게임 프로젝트라면 올릴 수 있음’, ‘인디 개발자와 소규모 개발팀, 개발사 대상’, ‘기록은 피드와 프로젝트에 함께 쌓임’이라는 답을 전달한다. 아래쪽에는 ‘만드는 과정부터 보여주세요’ 제목과 ‘오늘의 기록 하나가 프로젝트를 알리는 첫걸음이 됩니다’ 한 줄, 가장 아래에 ‘프로젝트 쇼케이스’ 이름을 넣는다. 버튼·링크 모양은 그리지 않는다. 위 ASCII 구조를 따르고 따뜻한 흰색·먹색·청록을 사용한다. 회원가입·알림 신청·출시 날짜·가짜 연락처, ‘개발 예정’ 라벨은 추가하지 않는다.

**UI-008 · UI 목업 생성 프롬프트**

> 세로 4:5 한국어 랜딩 페이지 하단 UI 목업을 만들어라. 위 ASCII처럼 ‘자주 묻는 질문’ 아래 질문 3개를 놓는다. 첫 질문 ‘어떤 프로젝트를 올릴 수 있나요?’만 펼쳐 ‘앱, 웹, 게임처럼 직접 만들고 있는 프로젝트라면 올릴 수 있습니다’라는 답을 보여준다. 아래 질문은 ‘누구를 위한 서비스인가요?’, ‘기록은 어떻게 쌓이나요?’. 이어지는 옅은 청록 배경의 마무리 영역에 ‘만드는 과정부터 보여주세요’와 ‘화면 둘러보기’ 버튼을 배치한다. 푸터에는 ‘프로젝트 쇼케이스 · 개발 기록으로 프로젝트를 알리다’와 ‘처음으로’. 이메일 폼·소셜 아이콘·가격·가짜 회사명은 넣지 않는다.

| BR-001 | 서비스를 이미 사용할 수 있는 프로덕트처럼 현재형으로 소개한다. ‘개발 예정’, ‘콘셉트’, ‘준비 중’, 개발 기간·공개 일정 같은 제작 상태 표현을 사이트 문구와 이미지에 쓰지 않는다. |
| BR-002 | 서비스 화면은 ‘작은 타이머’ 한 프로젝트로 일관되게 구성한다. 이용자 수·후기·성과 수치·가격·수상 내역 등 확인되지 않은 사실은 만들지 않는다. 화면 속 프로젝트가 예시라는 점은 `S-04` 하단의 작은 캡션으로만 알린다. |
| BR-003 | 실제 동작 요소는 소개 페이지의 앵커 이동과 FAQ다. 화면 이미지 속 카드·아이콘은 비상호작용이며 버튼처럼 포커스되지 않는다. |
| BR-004 | 정식 이름이 없으면 ‘프로젝트 쇼케이스’를 사용한다. 가입·다운로드·앱스토어·연락처·외부 채널 링크는 실제 주소가 생긴 뒤에만 추가한다. 공개 화면에 미완성 토큰이나 막힌 버튼을 남기지 않는다. |
| BR-005 | 이미지가 없는 상태에서도 핵심 문구와 화면 내용은 읽을 수 있다. 주요 제목·안내·CTA를 이미지 텍스트로만 제공하지 않는다. |
| BR-006 | 카피·와이어프레임을 바꾸면 연결된 프롬프트도 함께 바꾼다. 이번 문서의 범위를 실제 서비스 설계로 확장하지 않는다. |

| 상태 | 사용자에게 보이는 내용 | 처리 기준 |
|---|---|---|

## 8. 범위 및 제작 완료 기준

### 소개 사이트 기본 제작 범위

단일 페이지, 7개 본문 섹션, 반응형 레이아웃, 앵커 이동, FAQ, 정적인 서비스 화면을 포함한다. 화면 이미지 제작 전에도 텍스트 카드로 제작을 진행할 수 있다.

### 이후 선택적으로 보완할 것

정식 서비스명·실제 서비스 주소·가입/다운로드 링크·실제 스크린샷은 준비되면 추가하거나 교체한다. 별도 기능이나 모집 절차를 추가하려면 소개 사이트 범위를 먼저 갱신한다.

### 향후 사이트 완료 확인표

아래는 **제작 후 확인할 기준**이며, 지금 통과했다는 의미가 아니다.

- [ ] 처음 보는 사람이 첫 화면을 읽고 ‘인디 개발자와 작은 개발팀이 개발 기록으로 프로젝트를 알리는 서비스’라고 설명할 수 있다.
- [ ] 헤더·히어로·마지막 CTA의 목적지가 모두 유효하다. (`FR-001`)
- [ ] 같은 기록이 피드 화면과 프로젝트 화면에 연결되어 보인다. (`FR-002`)
- [ ] 사이트 문구와 이미지에 ‘개발 예정’·‘콘셉트’·개발 기간 같은 제작 상태 표현이 없다. (`BR-001`)
- [ ] 자주 묻는 질문 3개가 키보드로 동작한다. (`FR-003`)
- [ ] 360px·390px·768px·1440px에서 가로 넘침이 없고 링크와 본문이 읽힌다. (`FR-004`)
- [ ] 이미지 실패 시에도 핵심 설명을 읽을 수 있다. (`BR-005`)
- [ ] 허구의 실적·후기·가짜 외부 링크·동작하지 않는 가입 버튼이 없다. (`BR-002`, `BR-004`)

## 9. 첨부 자료 반영과 후속 연결

**기획 근거:** 참조 대화 「프로젝트 아이디어 추천」의 소개 사이트 분리 요청과 인디 개발자·개발사 타깃 명확화 요청, 개발 기록을 통한 프로젝트 홍보 방향, 이미지·영상·짧은 글 중심의 표현, ASCII와 이미지 생성 프롬프트 병행 요구를 반영했다. 과거에 제안된 여행·예약·테스터 모집 등은 현재 방향에 포함하지 않는다.

**v1.2 변경:** 사이트가 ‘개발 예정인 프로젝트 소개’처럼 보이지 않고 이미 있는 프로덕트를 홍보하는 사이트처럼 보이도록 요청받아 반영했다. ‘개발 예정·콘셉트·40일·공개 일정 미정’ 표현을 제거하고, `S-05`를 40일 제작 방향에서 시작하기 3단계(`#start`)로, FAQ를 서비스 이용 질문으로, CTA를 ‘화면 둘러보기’로 바꿨다. 확인되지 않은 실적·가격·후기와 가짜 가입 링크 금지는 유지한다.

**구조 근거:** `project_team_docs_lite.zip`의 `01_PRODUCT_SPEC.md` 순서인 한 줄 정의 → 목표/제외 → 사용자 → 흐름 → FR → 화면 → BR → 완료 기준을 사용했다. UI와 프롬프트는 이 문서에 통합했다. 기술·현황·작업 흐름은 원본의 정본 분리 원칙을 유지한다.
